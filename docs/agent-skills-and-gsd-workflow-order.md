# 에이전트 스킬·GSD 적용 순서 지침

Cursor·Claude Code 등에서 **여러 스킬(또는 커스텀 SKILL.md)** 과 **GSD(Get Shit Done, `.pi/gsd/` 번들)** 를 같이 쓸 때의 권장 순서다. 다른 프로젝트로 복사해 그대로 참고해도 된다.

---

## 1. 한 줄 요약

**GSD를 항상 맨 먼저 둘 필요는 없다.**  
먼저 **불확실성(무엇을 만들지·왜)** 을 줄일지, 아니면 **실행 계획(어떻게 쪼개 진행할지)** 을 고정할지에 따라 순서가 갈린다.

---

## 2. 의사결정 분기

| 상황                                               | 권장 선행 작업                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 목표·범위가 모호함                                 | 브레인스톰·요구 탐색(대화 또는 전용 스킬)                                                         |
| 제품 방향·트랙·지표가 비어 있음                    | 전략/로드맵 문서 정리 후 플랜                                                                     |
| **이미 PRD·요구 문서가 구체적**                    | PRD·Taskplane(또는 이슈 트래커)를 **입력**으로 GSD **`/gsd-plan-phase`** 등 실행 단에 가깝게 사용 |
| 기존 코드베이스가 크고 오래됨                      | GSD **`/gsd-map-codebase`** 또는 동등한 맵핑을 **플랜 직전**에 수행                               |
| 처음부터 GSD 산출물(`.planning/`)로 끝까지 갈 계획 | **`/gsd-new-project`** 등 초기화는 앞쪽에 둬도 됨 — 단, 모호하면 그 앞에 탐색 한 패스             |

---

## 3. GSD를 “비교적 앞”에 두기 좋은 경우

- `.planning/` 아래 **PROJECT · ROADMAP · 단계별 실행** 구조로 일관되게 가져갈 때
- 브라운필드에서 **`/gsd-map-codebase` → 계획·실행** 순이 자연스러울 때
- 넓은 아이디어 탐색보다 **곧바로 페이즈 단위 실행**이 목표일 때

GSD 공식 흐름 예시는 `.pi/gsd/workflows/help.md` 의 “Core Workflow”를 참고한다.

---

## 4. GSD보다 “앞”에 두는 편이 나은 경우

- **스코프·용어·우선순위 합의**가 필요할 때 (브레인스톰, 워크숍, 짧은 RFC)
- **PRD/요구사항 ID·비기능 요구**가 이미 있고, GSD는 **그걸 페이즈·토도로 쪼개는 도구**로만 쓸 때
- **외부 제약**(인증 방식, 배포, 규제)을 문서에 고정한 뒤 계획해야 할 때

이때 GSD를 “요구를 처음부터 다시 발명”하는 도구로 쓰면 중복·드리프트가 생기기 쉽다.

---

## 5. 이 저장소(academy-manage)에 맞춘 권장 적용

- **단일 원천**: 제품 요구는 **`docs/PRD.md`** (및 [web-project-common.md](web-project-common.md)) 를 우선한다.
- **작업 영역 메타**: `.pi/taskplane-config.json` 의 `taskAreas` 등으로 우선순위를 잡았다면, GSD 페이즈는 그 영역과 **정렬**하는 것이 좋다.
- **구현 갭**: 코드가 이미 있다면 **`/gsd-map-codebase`**(또는 동일 목적의 감사)로 문서와 코드의 차이를 맞춘 뒤 **`/gsd-plan-phase`** 로 페이즈를 깐다.
- **`.planning/`이 없을 때**: GSD “신규 프로젝트”를 반드시 처음부터 돌리기보다, PRD를 붙잡고 **맵 → 페이즈 계획 → 실행** 순으로 가져가도 된다.

---

## 6. 다른 프로젝트로 옮길 때

- 이 파일만 복사해도 되고, 프로젝트별로 **“원천 요구 문서 경로”** 와 **작업 영역 설정 파일 경로**만 치환하면 된다.
- GSD 번들은 `npx get-shit-done-cc@latest` 등으로 갱신하고, 팀에서 **커맨드 이름(`/gsd-*`)과 버전**을 짧게 README나 CONTRIBUTING에 적어 두면 혼선이 줄어든다.
