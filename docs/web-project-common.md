# 웹 프로젝트 공통 가이드 (재사용용)

이 문서는 **특정 도메인(학원 등)과 무관하게**, 웹 애플리케이션 개발에서 반복되는 관행을 정리한다.  
**다른 저장소로 통째로 복사**해 프로젝트명·스택에 맞게 최소만 고치면 재사용할 수 있도록 작성했다.

프로젝트별 요구사항(PR)·체크리스트 세부 항목은 별도 파일로 둔다.

에이전트(Cursor·Claude Code 등)에서 **스킬 적용 순서·GSD(Get Shit Done) 활용**을 정할 때는 **[agent-skills-and-gsd-workflow-order.md](agent-skills-and-gsd-workflow-order.md)** 를 참고한다. 다른 저장소로 이 공통 가이드만 복사할 때는 위 파일을 **같이** 두는 것을 권장한다.

**자율 실행**(세부는 에이전트가 추론)과 **추론 기록**은 **[agent-autonomy-policy.md](agent-autonomy-policy.md)**, **[inferred-decisions-log.md](inferred-decisions-log.md)** 를 따른다.

저장소 루트에 두는 **에이전트 운영 원칙**(Git·서브에이전트·검증·**caveman + `[CRITICAL]` 통신** 등) 파일명 관례는 **`AGENTS.md`** 이다(프로젝트별로 추가).

## 1. 배포·어댑터(프레임워크 배포 단위)

웹 프레임워크는 보통 **어댑터(adapter)** 로 빌드 결과를 특정 런타임(Node, 서버리스, 정적 호스트 등)에 맞게 묶는다.

- 로컬 개발만 할 때는 어댑터 선택이 크게 중요하지 않을 수 있다.
- 클라우드 이전 시 **목표 플랫폼이 정해진 뒤** 해당 플랫폼 문서에 맞는 어댑터를 고른다.

(예: SvelteKit은 `@sveltejs/adapter-*` 계열, Next.js는 호스팅 벤더별 설정 등.)

---

## 2. 환경 변수 정책

- **`.env.example`**: 사용하는 변수를 **전부 나열**하고, 각각 **주석으로** 목적·허용 값·환경별 주의사항을 적는다. **커밋한다.**
- **`.env`**: 실제 비밀값·로컬 전용 값. **커밋하지 않는다.**
- 애플리케이션 코드에서는 각 프레임워크가 권장하는 방식으로 로드한다.  
  (예: SvelteKit `$env/static/private`, `$env/dynamic/private`; Next.js `process.env` + 번들 규칙 등.)

### 2.1 운영·테스트 모드 전환(예시 패턴)

| 단계             | 목적                  | 설정 방향(개념)                               |
| ---------------- | --------------------- | --------------------------------------------- |
| 목업·UI 테스트   | 로그인 없이 빠른 검증 | 테스트용 **세션 주입(가장/impersonate)** 활성 |
| 통합·실사용 검증 | 실제 OAuth·세션 흐름  | 가장 비활성, 실인증 경로 + 제공자 키 설정     |

프로덕션에서는 테스트용 세션 주입이 **절대 켜지지 않도록** 환경 검증·코드 가드를 둔다.

### 2.2 인증 관련 동작(개념)

- **실제 로그인**: 선택한 인증 라이브러리의 세션·OAuth 경로.
- **가장 로그인**: 고정 테스트 사용자로 세션만 주입(E2E·수동 QA). 실제 제공자 호출 없음.

레거시 **목(mock) 객체**와 가장 로그인은 목적이 다르다. 문서와 코드에서 구분한다.

---

## 3. 인증 vs 데이터 접근(역할 분리)

- **인증 전용 라이브러리**(예: Better Auth, Auth.js 등): 로그인·세션·OAuth·토큰 교환 등 **신원 증명** 담당.
- **ODM/ORM 또는 DB 클라이언트**(예: Mongoose, Prisma, Drizzle): **업무 데이터** 스키마·쿼리. **“로그인 프로토콜”을 대신 제공하지 않는다.**

제품에서 **역할·테넌트·권한 범위**는 업무 DB(멤버십 테이블 등)와 서버 측 검증으로 처리하고, 클라이언트 표시만으로 신뢰하지 않는다.

---

## 4. 접근성(간단 목표)

- **WCAG(Web Content Accessibility Guidelines)**: 웹 접근성 국제 지침. 전 제품을 특정 등급(예: AA)으로 **공식 인증**하는 것과, **개발 시 참고**하는 것은 별개다.
- **실무 최소 목표**: 논리적 제목 구조, 폼 레이블 연결, **로그인 첫 포커스를 식별자 입력란**에 두기, 의미 있는 탭 순서, 주요 동작을 키보드로 수행 가능하게 하기.

---

## 5. 테스트 전략

- **단위·통합 테스트**: 도메인 로직·서버 유틸에 유지한다. (예: Vitest, Jest 등 프로젝트 표준 도구.)
- **E2E**: Playwright 등으로 **실제 브라우저**에서 클릭·입력 기반 검증. 실계정이 필요하면 자격 증명은 **저장소 밖**(CI Secrets 등)에만 둔다.

---

## 6. 외부 등록·비밀 작업(체크리스트 운영)

OAuth 앱 등록, 클라우드 Secrets, 금융·결제 API 계약 등은 **코드가 아니라 체크리스트**로 관리한다.

- 프로젝트마다 `docs/` 등에 **「개발자가 처리할 항목」** 류 문서를 두고, 스프린트 시작·배포 전에 해당 섹션을 연다.
- 공통 **형식**(언제 열지, 체크 표기, 비밀 비커밋 원칙)은 이 파일과 동일하게 유지하고, **제공자 이름·법규** 등 세부는 프로젝트 파일에만 적는다.
